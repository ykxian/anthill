# 00 · 产品需求文档（PRD）

## 1. 背景与动机

### 1.1 项目背景

- 开发者（本人）在日常多人协作开发中，实践过一个朴素但有效的 Agent 通信机制：
  让 Claude Code 监控一个指定文件夹，其他人想让这个 Agent 处理什么，就往文件夹里放文件；
  Agent 自动处理后，把回执写到对方指定的目录。几天实践证明该机制可用。
- 这个土办法背后是一个成熟的分布式思想：**通过共享环境中的持久化痕迹进行异步通信**
  （Maildir 邮箱模式 / Stigmergy）。本项目将它工程化、协议化，并扩展到跨机器场景。
- 同时借鉴两个开源项目：collab-cli（文件协议 + LAN 发现）和 clowder-ai（多模型
  Agent 团队编排），做一个**体量适合个人、但设计完整**的多 Agent 协同系统。

### 1.2 项目目标（按优先级）

1. **学习目标**：吃透 Agent Loop（LLM + 工具调用）、异步 IO、进程间/跨机器通信、
   简单的服务发现与认证 —— 每一块都能在面试中讲出"为什么这么设计"。
2. **秋招目标**：产出一个有真实差异点（跨机器文件邮箱协议）、可录屏演示、
   README 完整的开源项目。
3. **实用目标**：替代目前团队里手工搭建的文件夹监控方案，真的能用。

### 1.3 非目标（明确不做）

- ❌ 不做通用 Agent 平台（不做用户系统、多租户、插件市场）
- ❌ 不做公网穿透 / NAT 打洞（跨公网统一走 SSH）
- ❌ 不追求高吞吐消息队列的性能指标（文件邮箱天然不适合，也不需要）
- ❌ 不做复杂前端（Web 面板只读、单页、无构建链）
- ❌ MVP 不做移动端、语音、持久化数据库（文件即数据库）

## 2. 用户与场景

目标用户就是开发者自己和身边同学，两类典型场景：

### 场景 A：单机多 Agent 协同完成任务（核心演示场景）

```
$ anthill run "为 utils/date.py 补齐单元测试并让 reviewer 把关"
```

coordinator 拆解任务 → coder Agent 写测试 → 自动 @reviewer →
reviewer Agent（可以是另一个模型）给出审查意见 → coder 修改 → 汇总结果给用户。
全程 Agent 间消息在终端/Web 面板可见。

### 场景 B：本地 Agent 与服务器 Agent 协作（SSH 场景）

本地 Agent 负责与用户交互和写代码，服务器上的 Agent 负责在真实环境执行
（跑测试、看日志、部署）。两者通过 SSH 通道互投邮箱消息，回执确认执行结果。
**默认互相不可见**，需要显式配置对端。
（M9 修订：默认改为**互相可见**，因为手动互告地址太劝退；
但"要互投消息必须人工配对"这条硬要求没有变 —— 见 04-roadmap 的 M9 小节。）

### 场景 C：局域网内同学之间的 Agent 互助（opt-in）

实验室局域网内，显式开启 discovery 的 Agent 可以互相发现，
经用户确认配对后，可以互发任务（如"帮我用你机器上的 GPU 跑一下这个脚本"）。

## 3. 功能需求

### P0（MVP 必须有）

| 编号 | 功能 | 说明 |
|------|------|------|
| F1 | 消息信封协议 | 统一 JSON envelope，pydantic 严格校验，见 02-protocol |
| F2 | 文件邮箱 | Maildir 式目录（tmp/new/cur），原子写入，崩溃安全 |
| F3 | Agent 守护进程 | `anthill agent start`，监控自己邮箱，处理消息，写回执 |
| F4 | 三级回执 | delivered（送达）/ accepted（受理）/ completed（完成） |
| F5 | 自研 Agent Loop | LLM + 工具调用循环；工具：读写文件、受限 shell、发消息、结束 |
| F6 | 多模型 Provider 层 | Anthropic + OpenAI 兼容（DeepSeek/Qwen/GLM/OpenAI），按角色配模型 |
| F7 | 编排器 | coordinator 拆解任务、按角色分派、收集结果、汇总输出 |
| F8 | @mention 路由 | Agent 输出中 @某角色 时自动路由消息给对应 Agent |
| F9 | CLI | run / agent start / agent list / send / status / log |
| F10 | 执行策略引擎 | 危险操作（shell、删文件）分级，高危需人工确认（借鉴 collab-cli P0 机制） |

### P1（一期内做完）

| 编号 | 功能 | 说明 |
|------|------|------|
| F11 | LAN 发现 | UDP 组播 announce/probe，**默认关闭**，allowlist + 配对确认 |
| F12 | LAN 投递 | HTTP POST 投递信封 + HMAC 签名校验 |
| F13 | SSH 传输 | 通过 SFTP 直写远端邮箱目录，回执反向送回 |
| F14 | 共享黑板 | blackboard/ 目录：BOARD.md 当前状态 + decisions/ 决策记录 |
| F15 | Web 面板 | 只读：Agent 拓扑、实时消息流（WebSocket）、任务状态 |

### P2（二期 / 加分项）

| 编号 | 功能 | 说明 |
|------|------|------|
| F16 | Claude Code Adapter | 把"监控文件夹的 Claude Code"包装成标准 Agent 接入邮箱网络 |
| F17 | 跨模型互审工作流 | 内置 code-review 流程模板：A 模型写、B 模型审 |
| F18 | 消息重放与恢复 | 从邮箱历史重放任务现场，Agent 崩溃后续跑 |
| F19 | 心跳与故障转移 | Agent 心跳，超时后 coordinator 把任务改派他人 |

## 4. 参考项目分析（研究与重用结论）

| 项目 | 类型 | 可取之处 | 为什么不直接用 |
|------|------|---------|--------------|
| collab-cli | 文件协议 + CLI | 协议设计、LAN 发现思路、分层记忆 | 面向"人的 Claude Code 之间协作"，没有自研 Agent Loop 与编排 |
| clowder-ai | 重量级平台 | 角色/身份、A2A 路由、互审流程 | Node+Redis+Web 全家桶，体量远超个人项目；核心是包装现有 CLI |
| AutoGen / CrewAI / LangGraph | Python 框架 | 编排范式可参考 | 单进程内存内通信为主，无跨机器文件邮箱/发现/SSH 这些系统能力；直接用则失去学习和差异化价值 |

**结论**：协议与思想大量借鉴，代码自研；差异化定位 =
"跨机器、去中心、异构 Agent 可接入（含 Claude Code 这类现成 CLI）的轻量协同框架"。

## 5. 成功标准

1. 录屏演示三个场景（A/B/C）各一条，全流程无人工干预（除高危确认）。
2. 两个不同模型的 Agent 完成一次真实的"写码 + 互审 + 修改"闭环。
3. 单元 + 集成测试覆盖率 ≥ 80%（核心协议层接近 100%）。
4. README（中英）+ 架构图 + 快速开始，陌生人 10 分钟内能跑起来。
5. 面试时能对着 05-resume-interview.md 的每个问题给出流畅回答。

## 6. 风险

| 风险 | 影响 | 对策 |
|------|------|------|
| LLM API 成本 | 开发期反复调试烧钱 | 开发默认用 DeepSeek；provider 层做请求日志与回放 mock |
| 学校服务器是 NFS | inotify 失效收不到文件事件 | watcher 自动降级为轮询（详见 03-tech-design） |
| Agent 互相 @ 死循环 | 消息风暴 + 烧钱 | envelope 带 hop 计数与 TTL，超限熔断（详见 02-protocol） |
| Agent 间 prompt 注入 | 恶意/失控消息诱导执行危险操作 | 策略引擎 + 消息来源信任分级，shell 高危必确认 |
| 范围失控做不完 | 秋招前没有可演示成果 | 严格按 04-roadmap 里程碑走，每个 M 都可独立演示 |
