## 1. 简历条目模板

**AntHill —— 分布式多 Agent 协同框架**（个人项目，Python | 开源）

- 设计并实现基于文件邮箱（Maildir 变体）的 Agent 通信协议：ULID 信封 + tmp/rename
  原子写实现**无锁并发投递**，配合发送方重试与接收方幂等去重，达成"至少一次投递、
  恰好一次处理"语义；协议层测试覆盖率 ~100%
- 自研 ReAct 式 Agent Loop 与多模型接入层（Claude / DeepSeek / Qwen 等），支持
  按角色配置不同模型，实现"A 模型写码、B 模型审查"的跨模型互审工作流
- 实现中心编排 + 点对点 @mention 的混合协作模式：coordinator 以结构化 JSON 拆解
  任务、拓扑调度并发分派；hops-TTL 熔断防止 Agent 间消息死循环
- 统一传输抽象覆盖同机文件、局域网（UDP 组播发现 + HTTP 投递 + HMAC 签名防重放，
  默认关闭）、跨机 SSH/SFTP 三种场景，服务器侧**零端口开放**接入协作
- 单页零依赖的 Web 总控面板：各节点定期落一份状态快照，控制端按对端已有的传输方式
  并发汇聚（LAN 走签名 HTTP、SSH 走 SFTP），**单点不可达降级为标记而非阻塞整页**

（按 JD 取舍：投 AI 应用岗突出第 2/3 条，投后端/基础架构岗突出第 1/4/5 条。）

## 2. 一分钟叙事线（STAR）

  "监控文件夹 + 手动回执"的土办法，几天实践发现有效但不可靠（丢消息、无确认、无安全）。

  统一；在此之上做原子写、回执状态机、幂等、签名、编排。（然后按面试官兴趣展开某一层。）

## 3. 高频面试问答

### Q1 为什么用文件当消息队列，不用 Redis/RabbitMQ/Kafka？

要点：① 需求量级每秒远小于 100 条，MQ 的吞吐优势用不上，运维成本却是实打实的；
② 文件是唯一让"任何能读写文件的东西"（包括 Claude Code 这类现成 CLI、甚至人）
零 SDK 接入的介质；③ 消息即文件 → 天然持久化、可 `cat` 调试、可 git 审计、可重放；
④ 架构上传输是抽象接口，真要上量把 Transport 换成 MQ 实现即可，上层零改动。
加分句：这本质是 Maildir 的思想，qmail 用它三十年了；学术上叫 Stigmergy。

### Q2 怎么保证消息不丢、不重复？

分两半答。**不丢**：写入方 tmp 写完 fsync 再 rename（POSIX 同文件系统 rename 原子），
消费方永远见不到半个文件；发送方 outbox/pending 持久化 + 指数退避重试，重试耗尽进
dead letter 上报。**不重**：重试必然带来重复投递，接收方用 seen.db 按消息 ULID
去重，重复消息丢弃但补发回执让发送方状态机收敛。合成语义 = 至少一次投递 + 幂等消费
= 恰好一次处理。

### Q3 多个发送方并发写同一个邮箱，怎么处理竞争？

不处理——设计成不存在竞争：文件名是各自生成的 ULID，天然不冲突；rename 原子；
所以**无锁**。唯一的共享写点 seen.db 用 SQLite 自带的锁。追问"ULID 会撞吗"：
80 bit 随机数 + 时间戳前缀，同毫秒撞概率可忽略，且撞了也只是去重误杀一条、有回执可查。

### Q4 inotify 在 NFS 上不工作，你怎么发现和解决的？

学校服务器 home 目录是 NFS，inotify 事件由内核本地产生，远端写入不触发。
方案：agentd 启动时自检（写探针文件看事件是否到达），失败自动降级为轮询扫描
`new/` 目录，自检结果暴露在 `anthill status` 里方便排查。
这题价值在展示"知道抽象泄漏在哪"。

### Q5 为什么默认不广播？发现协议怎么设计的？

需求出发：一台机器/网段上可能有很多同学的 Agent，默认互相可见既是打扰也是安全隐患。
设计：discovery 默认完全关闭（零发包零监听）；开启后用 UDP **组播**（不是全网广播，
只有加组的进程收得到）；发现只建立"可见"，通信必须显式 `trust`（TOFU 记指纹 +
交换共享密钥）。三层递进：静默 → 可见 → 可通信。

### Q6 安全上防了什么？

① 伪造：跨节点消息 HMAC-SHA256 签名，密钥 per-peer；② 重放：时间戳窗口 5 分钟 +
ULID 去重双保险；③ Agent 间 prompt 注入：他人消息一律当不可信数据，定界包裹进上下文，
且消息内容永远不能直接触发高危工具——策略引擎按"工具风险 × 来源信任级"决定
allow/confirm/deny，远端来的 shell 命令必须本人确认；④ 路径逃逸：文件工具
规范化路径后做前缀校验；⑤ 密钥管理：配置只存环境变量名，仓库无密钥。

### Q7 和 AutoGen / LangGraph / CrewAI 什么区别？为什么不直接用？

它们解决"一个进程里多个 LLM 角色怎么编排"，通信在内存里；AntHill 解决的是
"**不同机器、不同所有者、异构实现**的 Agent 怎么协作"——跨机传输、发现、信任、
回执可靠性这些系统问题它们不覆盖。编排范式（结构化计划、角色分工）确实借鉴了它们。
另外项目动机之一是学习，核心轮子（agent loop、协议）刻意自研，但清楚生产上何时该用现成的。

### Q8 两个 Agent 互相 @ 出死循环怎么办？

信封带 hops 计数，因收到消息而发出的新消息 hops+1，超过 ttl_hops（默认 8）路由层
拒发并上报 coordinator；另有每 thread 消息数上限与每任务 token 费用熔断兜底。
三层防线对应三种失控形态：无限跳、无限聊、无限烧钱。

### Q9 SSH 场景为什么用 SFTP 直写，而不是在服务器起个服务？

服务器上开端口意味着认证、TLS、防火墙审批（学校网络尤其麻烦）。SFTP 直写复用已有的
SSH 信任与加密，服务器**零新增攻击面**；且"写文件到对方 inbox"和本地传输语义完全同构，
SshTransport 只有 ~100 行差异代码。代价是投递延迟高些（连接复用缓解），对本场景无所谓。

### Q10 多 Agent 的上下文怎么管理？

① thread 严格隔离，每个编排步骤开子 thread，防交叉污染；② 上下文预算控制在模型
窗口 70%，超长历史用便宜模型摘要压缩并落盘；③ 共享状态走 blackboard（BOARD.md
单写者 + 任务产物目录），消息体只传引用不传大文件。

### Q11 如果扩展到几百个 Agent、每秒几千条消息呢？

诚实版答案：文件邮箱会先倒下（目录 iter 变慢、轮询开销、SQLite 锁争用），这个设计
就不是为那个量级做的。但分层的价值在于：Transport/Mailbox 是接口，换成
Redis Streams 或 NATS 实现，L2 以上（回执语义、幂等、路由、编排）原样保留。
能主动说清自己方案的适用边界，比硬吹更加分。

### Q12 项目里踩过最深的坑？

（开发中随手往 `docs/pitfalls.md` 记，面试前挑一个有细节的。候选坑位：
NFS 上 inotify 静默失效；子进程 stderr 管道写满导致假死；rename 跨文件系统退化为
copy 失去原子性——tmp 必须和 new 同分区；LLM 结构化输出偶发缺字段的重试设计。）

### Q13 一个面板要管好几台机器，数据怎么汇？

先说不能怎么做：跨机没有共享文件系统，面板不可能直接去读别人的目录；
而逐个文件走 SFTP 拉又太碎（一次面板刷新几十次往返）。
所以**约定一个汇合点**：每个节点定期把自己的快照写成一个 `.anthill/status.json`，
总控只需要取那**一个**文件 —— 问题就退化成「怎么把一个文件从那边拿过来」，
而这条路每种传输本来就有：LAN 走 HTTP、SSH 走 SFTP。
**SSH 那侧不因为做面板而多开一个端口**，这是 M5 就定下的底线，不能为了方便破例。

三个细节值得讲：

1. **读也要认证，而且用同一把密钥**。新造一套令牌等于新造一处会泄露、会过期、
   会忘记轮换的东西。共享密钥已经在那儿了 —— 签 `域标签 + 节点 + 路径 + 时间戳`
   （域标签是为了让它和信封签名不能互相顶替），30 秒防重放窗
   （比信封的 5 分钟严：读请求是同步的，又没有 seen.db 那样的去重兜底）。
   「发现 ≠ 可通信」在读取方向上同样成立：未信任的节点只出现在拓扑里，
   总控不去读它的状态。
2. **一台连不上不能把整页卡住**。并发拉取 + 各自超时，拿不到就标「连不上」
   并把原因显示出来。分布式面板最常见的坏法就是一台机器挂了、整个页面转圈。
3. **写权限只对总控这台机器生效**。它发起的任务从本机 `cli` 出发，
   跨机那一段仍然走签名投递；能读别人的状态，但改不了别人的配置。

联调时揪出一个只有真跑起来才会看见的 bug：WebSocket 推的是本机快照，
会把总控视图里其他机器抹掉 —— 页面打开时三台都在，一秒后只剩本机。
根因是「实时」和「跨机」的刷新频率天然不同，硬塞进一条通道就会互相覆盖。
改成两路合成一张图：WS 只更新本机那一格，全集群走 5 秒一次的拉取。

**这个里程碑真正的收获在 review 那一轮**，而且可以归到同一句话上：
*多了一个数据来源，威胁模型就变了，但我写的时候还在用单机时代的假设。*
三个例子：

- `queue` / `dead` 这些数字，此前是本机 `len(mailbox.list_new())` 算出来的，
  前端插值不转义也无所谓；接上远端之后它们成了对端 JSON 里的任意值，
  而面板开了写权限时「在面板里执行 JS」约等于「在这台机器上执行命令」。
  补 `esc()` 是一次性的答案；**在进程边界上用 pydantic 校验整份快照**才是。
- 「读得到那个文件」不等于「那台机器活着」。SSH 那条路直接读对方磁盘上的
  `status.json`，对方 serve 被 kill 之后文件还在 —— 不看时间戳的话，
  一台死了一周的机器一直显示成绿灯，恰好把这个功能的招牌承诺反过来了。
- 一个「看看状态」的 GET 是**有副作用**的：每次可能触发 N 次 SSH 登录，
  浏览器 5 秒一轮询、多开标签页还翻倍，足够撞上服务器的 `MaxStartups`。

答这题时我会主动说这三条 —— 比只讲「我做了个总控面板」有信息量得多。
